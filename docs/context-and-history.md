# Context sizing, chat history and activity

The previous 32,768-token fallback reserved 4,096 output tokens plus safety overhead. Compaction began near 80% of the remaining input budget, so a chat could compact at roughly 22,000 estimated input tokens. A larger configured output reserve or skill payload lowered the available conversation space further. This was an application budget, not evidence that every model had a 32K window.

The default fallback is now 1,000,000 tokens. This is an application preference when capacity is unknown, not a promise that the provider supports one million tokens. In automatic mode the actual provider `/models` context metadata takes precedence. An explicitly configured manual window remains bounded by the provider's declared capacity. A provider that returns only model IDs does not verify the fallback capacity; users must check the provider's documentation or set a known manual window. The application does not infer capacities from model names.

Live Agent context stats, including the actual window, output reserve, input budget, usage and selected model, are persisted separately in SQLite `session_context`. Restoring an old chat shows the window used for that session rather than replacing it with today's configuration. Explicit `/compact` resolves the current model's effective limits before summarization. `limitSource=runtime` identifies an observed execution budget; it does not assert the provider independently confirmed that number. Legacy sessions without persisted stats resolve provider/manual/fallback limits when opened.

Visible chat history is independent of the model's compressed working memory. Restoration prefers display messages, then original archived user/assistant turns, then surviving conversation state. Tool calls and tool-result messages are excluded from display-history fallbacks. Legacy Teamwork sessions can reconstruct the goal and task results from the sessions/tasks tables. New Teamwork sessions persist their full user request and final assistant result. Failures preserve the displayed error and any streamed output.

The server emits `chat_session` to bind a submitted chat to its durable session ID, including Teamwork's generated ID. Session ordering uses monotonic update timestamps so continuing an older chat moves it to the top, even when multiple updates happen in the same millisecond. Completion broadcasts the refreshed session list.

`run_progress` stores session-scoped activity records. Ordinary tool-call and tool-result messages create start/end records; model selection and run completion are recorded as well. Teamwork lifecycle milestones use the same store. Live WebSocket records use `type=progress_event` plus `eventType` for the milestone kind; restored `conversation.progress` records retain their milestone `type`. Restored activity returns the most recent 500 records in chronological order. Tool arguments and outputs are not copied into progress records.

MCP settings are saved in project configuration and omitted from generic config/status responses. The dedicated `mcp_status` response strips header/environment credentials and sensitive arguments/query values. Editing safe status fields preserves omitted secret fields and the original URL query when the displayed sanitized URL is resubmitted unchanged. Disabled servers do not start during discovery.

Regression coverage: `tests/history-context.test.ts` checks archive/state/legacy restoration, ordering, real WebSocket context persistence after model changes, ordinary tool milestones, and MCP settings credential preservation/redaction. `tests/desktop.test.ts` covers chat history across named-agent model switches and unlimited-budget configuration.

## User pins and attached source files

Pins are explicit user actions; no model tool creates or edits them. Each pin has a stable ID, label, creation time and verbatim content. Pins and attached-file snapshots are protected context, kept across compaction and counted in the fixed request budget. If protected material cannot fit the selected model, preparation stops with an explicit error without deleting it. The user can remove selected pins/files or choose a larger supported window.

Attachments are workspace-local text snapshots, with path, byte size and SHA-256 identifying the original bytes. Their content is data rather than instructions; the model is told to inspect the current file before acting. External paths, internal state/credential directories, secret file names/key extensions, binary files and files over 1 MiB are rejected. Files over 32,768 estimated tokens are rejected rather than silently truncated. Common inline credentials/private keys in otherwise ordinary text are redacted; this is not a guarantee to detect every possible secret. Maximums are 20 file attachments and 32 pins (8,192 estimated tokens per pin).

The context inspector reports token estimates for system text, tool definitions, summary, protected sources and individual messages/complete tool groups. Summary source records retain compaction mode, message count, roles and time; the original durable archive is the source for omitted details. Token estimates are UTF-8 heuristics, not provider tokenizer or billing measurements. The inspector shows attachment metadata and bounded previews instead of returning whole file contents.

## Per-run token and cost budgets

`runBudget` optionally contains `maxTokens` and `maxCostUSD`; zero or absence means no cap. `modelRates` is an explicit user-configured map keyed by exact model ID with `inputPerMillion`, `outputPerMillion` and optional `cachedInputPerMillion` dollar rates. No default model price is invented. Cached input uses the configured cache rate or normal input rate when not supplied.

The tracker separates provider-reported and estimated tokens, counts model/tool requests, measures elapsed time and reports per-model usage with task/agent identity. It warns at 80% of configured budgets and stops before the next model request once the observed token cap or known cost cap is reached. A single already-started response can overshoot because the application cannot predict actual provider completion/charges. Summarization requests should use the same tracker through context accounting callbacks. Failed or interrupted calls may have provider charges not reported by the API.

Unknown model pricing remains `costUSD=null` and triggers a warning when a dollar budget is set. The tracker exposes the known priced subtotal separately; it does not claim to enforce an unknown provider bill. Estimated token usage leads to estimated cost, clearly flagged separately from provider usage. Budget stop errors should persist run progress/context before exiting so the user can review and resume with a new budget.
