# Context sizing, chat history and activity

The previous 32,768-token fallback reserved 4,096 output tokens plus safety overhead. Compaction began near 80% of the remaining input budget, so a chat could compact at roughly 22,000 estimated input tokens. A larger configured output reserve or skill payload lowered the available conversation space further. This was an application budget, not evidence that every model had a 32K window.

The default fallback is now 131,072 tokens. In automatic mode the actual provider `/models` context metadata takes precedence. An explicitly configured manual window remains bounded by the provider's declared capacity. A provider that returns only model IDs does not verify the fallback capacity; users must check the provider's documentation or set a known manual window. The application does not infer capacities from model names.

Live Agent context stats, including the actual window, output reserve, input budget, usage and selected model, are persisted separately in SQLite `session_context`. Restoring an old chat shows the window used for that session rather than replacing it with today's configuration. Explicit `/compact` resolves the current model's effective limits before summarization. `limitSource=runtime` identifies an observed execution budget; it does not assert the provider independently confirmed that number. Legacy sessions without persisted stats resolve provider/manual/fallback limits when opened.

Visible chat history is independent of the model's compressed working memory. Restoration prefers display messages, then original archived user/assistant turns, then surviving conversation state. Tool calls and tool-result messages are excluded from display-history fallbacks. Legacy Teamwork sessions can reconstruct the goal and task results from the sessions/tasks tables. New Teamwork sessions persist their full user request and final assistant result. Failures preserve the displayed error and any streamed output.

The server emits `chat_session` to bind a submitted chat to its durable session ID, including Teamwork's generated ID. Session ordering uses monotonic update timestamps so continuing an older chat moves it to the top, even when multiple updates happen in the same millisecond. Completion broadcasts the refreshed session list.

`run_progress` stores session-scoped activity records. Ordinary tool-call and tool-result messages create start/end records; model selection and run completion are recorded as well. Teamwork lifecycle milestones use the same store. Live WebSocket records use `type=progress_event` plus `eventType` for the milestone kind; restored `conversation.progress` records retain their milestone `type`. Restored activity returns the most recent 500 records in chronological order. Tool arguments and outputs are not copied into progress records.

MCP settings are saved in project configuration and omitted from generic config/status responses. The dedicated `mcp_status` response strips header/environment credentials and sensitive arguments/query values. Editing safe status fields preserves omitted secret fields and the original URL query when the displayed sanitized URL is resubmitted unchanged. Disabled servers do not start during discovery.

Regression coverage: `tests/history-context.test.ts` checks archive/state/legacy restoration, ordering, real WebSocket context persistence after model changes, ordinary tool milestones, and MCP settings credential preservation/redaction. `tests/desktop.test.ts` covers chat history across named-agent model switches and unlimited-budget configuration.
